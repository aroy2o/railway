## 1. Readiness Tiers

**Tier 1 — SOLVER-READY.** Gate: CP-SAT can consume the data and produce a
plan with zero hard-constraint violations and a reason on every unscheduled
task.

Pass criteria: 0 task→plan location mismatches · 100% of the 35-day horizon
covered by resource availability · both directions present in forecast/occupancy
· 100% of solver-relevant assets resolve `station_code`+`block_section` via
`location_id` · every task's resource need is an individually addressable row,
not a joined string · isolation/buffer/alt-routing/block-compatibility data
exists · plan outputs carry delay-cost, availability-gain, bundling-benefit,
solver-status, unscheduled-reason fields.

Files: `assets.csv`, `network_locations.csv`, `maintenance_tasks.csv`,
`resource_availability.csv`, `train_forecast.csv`, `corridor_occupancy.csv`,
`block_plan_weekly.csv`, `block_plan_monthly.csv`, new
`task_resource_requirements.csv`, new constraint tables.

**Tier 2 — ML-READY.** Gate: the training/evaluation *code path* can run
correctly end-to-end on synthetic data with no leakage — this proves the
pipeline, not real predictive accuracy. Real accuracy claims stay blocked
until real historical outcomes replace synthetic labels (same principle
`risk.py` already applies: a classifier trained on labels generated by the
same process as its features is circular and unmeasurable).

Pass criteria: one row per `task_id` in the feature store (not per asset) ·
every feature carries an `as_of_timestamp` · labels
(`actual_duration_minutes`, `actual_train_delay_minutes`,
`failure_within_30_days`) are explicitly defined and time-ordered ·
time-based (not random) train/val/test split is possible · a rules-based
baseline runs and is measured before any model.

Files: rebuilt `ml_feature_store.csv` (task-keyed),
`historical_block_outcomes.csv`, `defects.csv`, `maintenance_tasks.csv`,
`corridor_occupancy.csv`.

**Tier 3 — DEMO-GRADE.** Gate: every record is labeled real/derived/synthetic,
the solver runs clean, three scenarios (high traffic, resource shortage,
critical defect) reproduce from the data, baseline-vs-AI is reproducible from
output tables, and no synthetic number is presented as real-world accuracy.

Files: all canonical inputs + `block_plan_weekly/monthly.csv` +
`kpi_summary.csv`, each at one canonical path with a provenance record.

## 4. Volume Strategy

| Table | Current | Demo target | Pipeline-validation target | Time span | Grounding |
|---|---|---|---|---|---|
| Stations | 22 | 22 | 22 | — | Real; do not scale |
| Block sections | 65 | 65 | 65 | — | Real; do not scale |
| Resources | 9 | 9–15 | 15–20 | — | Modest realistic crew/machine pool growth, not arbitrary duplication |
| Defects | 112 | 112 | 1,500 | 12 months | Beta-skewed severity per PRD §5.2, department mix 50/30/20 |
| Maintenance tasks | 112 | 112 | 1,500 | 12 months | 1:1 to 1:2 per defect, same generator logic already in use |
| Historical outcomes | 112 | 112 | 1,500 | 12 months | Extends existing `historical_block_outcomes.csv` distribution, not a new one |
| Resource availability | 7 days | 35 days | 12 months | 12 months | Calendar extension of WR7, includes synthesized planned absences |
| ML feature store | 262 (wrong grain) | 112 (task-keyed) | 1,500 (task-keyed) | matches tasks | Rebuilt per Section 3b |

**Decisive call on the number:** 1,500, not 5,000+. A 12-month span at the
existing 0–3-tasks-per-asset generation rate produces roughly this order of
magnitude on its own — going higher manufactures a volume the generator's
own logic doesn't organically produce, which is the same "looks rigorous,
isn't" problem this whole review exists to avoid. 1,500 rows across 12 months
is enough to exercise a time-based train/val/test split meaningfully; it is
not, and should never be presented as, evidence of real-world model accuracy.

**Why 12 months, not 24:** the real freight/passenger/infrastructure data
stays exactly as-is at its real span — this scale-up only touches the
synthetic maintenance layer. 12 months covers one full seasonal cycle, which
is what the risk model's decline-rate logic and the weather-risk feature both
need; 24 months adds volume without adding a second real basis for anything.

**Referential integrity while scaling:** generate parents before children
(asset → defect → task → block_request → outcome), deterministic IDs,
validate every foreign key after each generation stage, record the
generation seed.

**Do not scale:** stations, block sections, platforms/lines, signal topology,
curvature/gradient/PSR — all real, fixed reference data; more rows here would
misrepresent the corridor, not describe it better.

## 5. Data Lineage & Source-of-Truth Decisions

- **Official directory:** `data_raw/synthetic/*.csv` (root, flat). Nested
  mirrors deleted per WR10 — nothing references them, and this matches the
  flat `raw/processed` convention already used in `data/`.
- **Canonical names: keep current names.** `ml_feature_store.csv`,
  `historical_block_outcomes.csv`, `kpi_summary.csv` stay as-is — no rename
  to `task_ml_features.csv`/`maintenance_history.csv`/`plan_kpis.csv`. The
  PRD's actual data model (§15) is MongoDB collections, not these CSV names;
  renaming has zero functional benefit and only risks breaking whatever
  ingestion code later reads these paths.
- **Immutable inputs (post-WR3/WR5):** cleaned infrastructure, route,
  passenger timetable, freight history, `network_locations.csv`.
- **Regeneratable:** defects, maintenance_tasks, block_requests, resources,
  resource_availability, forecasts, corridor_occupancy, ml_feature_store,
  block_plan_weekly/monthly, kpi_summary — all reproducible from generator +
  seed.
- **Freight nulls: keep null, never impute.** Block Km/Hrs/Speed feed
  safety-relevant delay and capacity calculations — fabricating a
  plausible-looking value here is the exact category of invented number this
  project's own conventions forbid. Exclude invalid rows from statistical
  fitting, retain the row with its `data_quality_flag`, report the excluded
  volume in the data-quality report.

## 7. Risk Register

| Risk | What breaks | Early warning | Mitigation |
|---|---|---|---|
| Synthetic ML results read as real accuracy | Indefensible claims in front of judges | High test metrics with no real historical backing | Label every Tier-2 output "pipeline validation only" — matches the precedent already set in `risk.py` |
| DN-only forecast hides real UP conflicts | Solver books a block during a real train movement | One-sided direction distribution | WR8 |

| Freight invalid values re-enter derived stats | Delay/traffic estimates skew from unflagged outliers | Negative/extreme values reappear in `Speed_Calculated` | WR3/WR4 + the null-not-impute policy |
| Asset-level feature store silently misjoined as task-level | Downstream code joins 262 asset rows against 112 tasks and gets duplicated or missing features | Row-count mismatch (262 vs 112) surfaces late, in the solver or model, not at the data layer | WP11 |

## 8. Judge-Facing Data Narrative

- Infrastructure, route, passenger timetable, and freight movement data are
  real corridor records from the KTV-PSA network — not simulated.
- Forecasts and occupancy are derived from that real timetable and real
  freight history, not invented from scratch.
- Maintenance defects, tasks, resources, and outcomes are synthesized,
  because TMS/SMMS/TDMS/BDMS operational exports are internal to Indian
  Railways and unavailable to an external team — synthesized, but anchored to
  real station codes, block sections, and departmental work patterns, not
  generic placeholder data.
- Any predictive score shown is trained on simulated data and explicitly
  described as such; it demonstrates the pipeline and the constraint logic,
  not real-world predictive accuracy, until real historical outcomes replace
  the synthetic labels.
